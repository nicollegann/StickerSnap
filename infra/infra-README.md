# StickerSnap Infrastructure

This directory contains the AWS CDK app for StickerSnap. The stack provisions the cloud resources for both development and production processing, plus the frontend hosting layer.

## What CDK Creates

- `AssetsBucket`: production S3 bucket for `uploads/` and `outputs/`
- `AssetsBucketDev`: development S3 bucket for `uploads/` and `outputs/`
- `ProcessingLambda`: production Docker Lambda
- `ProcessingDevLambda`: development Docker Lambda
- One Lambda Function URL for each processing Lambda
- `FrontendBucket`: private S3 bucket for the built Vite app
- `FrontendDistribution`: CloudFront distribution using S3 Origin Access Control
- GitHub OIDC provider and `GitHubActionsDeployRole`
- IAM permissions for Lambda, S3, ECR asset publishing, CloudFront invalidation, and CI/CD
- CloudFormation outputs for the names and URLs needed by local development and deployment scripts

## Files

### `bin/infra.ts`

Creates the CDK app and registers `StickerSnapStack`.

- Uses `CDK_DEFAULT_ACCOUNT` from the CDK CLI environment.
- Uses `CDK_DEFAULT_REGION`, falling back to `ap-southeast-1`.
- Tags stack resources with `Project: StickerSnap` and `ManagedBy: CDK`.

### `lib/stickersnap-stack.ts`

Defines all AWS resources. The current stack intentionally has separate dev and production processing resources, while sharing one frontend hosting layer.

### `cdk.json`

Runs the app with:

```json
"app": "npx ts-node --prefer-ts-exts bin/infra.ts"
```

The `watch` block excludes generated and dependency files. The `context` block contains CDK feature flags generated by CDK and should generally be left in place.

### `package.json`

Useful scripts:

| Script | Command | Purpose |
| --- | --- | --- |
| `npm run build` | `tsc` | Compile the CDK TypeScript |
| `npm run watch` | `tsc -w` | Watch and compile |
| `npm run deploy` | `cdk deploy --require-approval never` | Deploy the stack |
| `npm run diff` | `cdk diff` | Preview stack changes |
| `npm run synth` | `cdk synth` | Generate CloudFormation locally |
| `npm run destroy` | `cdk destroy` | Destroy stack-managed resources |

## Resources

### Assets Buckets

| Construct | Bucket name pattern | Environment |
| --- | --- | --- |
| `AssetsBucket` | `stickersnap-assets-{account}-{region}` | Production |
| `AssetsBucketDev` | `stickersnap-assets-dev-{account}-{region}` | Development |

Both buckets use the same shape:

| Setting | Value |
| --- | --- |
| Public access | Blocked |
| Encryption | S3 managed |
| SSL | Enforced |
| Removal policy | `RETAIN` |
| Lifecycle | Delete `uploads/` and `outputs/` objects after 1 day |
| CORS | `GET`, `PUT`, `HEAD`; allowed headers `*`; allowed origins currently `*` in CDK |

The browser uploads resized images directly to `uploads/` through a presigned `PUT` URL. Lambda writes processed stickers to `outputs/` and returns a presigned `GET` URL.

### Processing Lambdas

| Construct | Bucket | Purpose |
| --- | --- | --- |
| `ProcessingLambda` | `AssetsBucket` | Production processing |
| `ProcessingDevLambda` | `AssetsBucketDev` | Development processing |

Both are `lambda.DockerImageFunction` resources using the same Docker image from `../lambda/Dockerfile`. CDK builds the image with `ecr_assets.DockerImageAsset`, pushes it to a CDK-managed ECR asset repository, and wires the image into both functions.

Important settings:

| Setting | Value |
| --- | --- |
| Memory | `3008 MB` |
| Timeout | `120 seconds` |
| Platform | `LINUX_AMD64` |
| Function URL auth | `NONE` |
| Function URL CORS | `POST`, `content-type`, origin `*` |

Environment variables:

| Variable | Value |
| --- | --- |
| `BUCKET_NAME` | Environment-specific assets bucket |
| `UPLOADS_PREFIX` | `uploads/` |
| `OUTPUTS_PREFIX` | `outputs/` |
| `PRESIGNED_URL_EXPIRY_SECONDS` | `3600` |
| `BORDER_SIZE_PX` | `12` |
| `MAX_IMAGE_DIMENSION_PX` | `1024` |
| `NUMBA_CACHE_DIR` | `/tmp/numba_cache` |
| `NUMBA_DISABLE_JIT` | `0` |
| `U2NET_HOME` | `/tmp/u2net` |
| `XDG_CACHE_HOME` | `/tmp/cache` |
| `HOME` | `/tmp` |

IAM access:

- Dev Lambda can `PutObject` to `uploads/*`, `GetObject` from `uploads/*`, `PutObject` to `outputs/*`, and sign `GetObject` URLs for `outputs/*` in the dev bucket.
- Production Lambda has the same permissions against the production bucket.

### Frontend Bucket

`FrontendBucket` stores the built Vite app from `frontend/dist`.

| Setting | Value |
| --- | --- |
| Bucket name pattern | `stickersnap-frontend-{account}-{region}` |
| Public access | Blocked |
| Encryption | S3 managed |
| SSL | Enforced |
| Removal policy | `RETAIN` |

The bucket is private. CloudFront reads from it through Origin Access Control.

### CloudFront

`FrontendDistribution` serves the React PWA.

| Setting | Value |
| --- | --- |
| Origin | `FrontendBucket` with Origin Access Control |
| Viewer protocol | Redirect HTTP to HTTPS |
| Cache policy | `CACHING_OPTIMIZED` |
| Compression | Enabled |
| Default root object | `index.html` |
| SPA fallback | 403 and 404 return `/index.html` with status 200 |

### GitHub Actions OIDC Role

The stack creates a GitHub OIDC provider and `StickerSnapGitHubActionsRole`. This avoids long-lived AWS credentials in GitHub.

The role currently trusts:

```text
repo:YOUR_GITHUB_ORG/stickersnap:*
```

Replace `YOUR_GITHUB_ORG/stickersnap` with the real GitHub owner and repository before relying on CI/CD.

Current permissions include:

- Pull/push access to the CDK-managed Lambda image repository
- `lambda:UpdateFunctionCode` for both processing Lambdas
- Lambda invoke permissions for sanity checks
- Read/write access to the frontend bucket
- `cloudfront:CreateInvalidation` for the frontend distribution

## Outputs

After `cdk deploy`, CloudFormation exports:

| Output | Description |
| --- | --- |
| `AssetsBucketName` | Production assets bucket |
| `AssetsBucketNameDev` | Development assets bucket |
| `FrontendBucketName` | Frontend hosting bucket |
| `LambdaFunctionUrl` | Production Lambda Function URL |
| `LambdaDevFunctionUrl` | Development Lambda Function URL |
| `CloudFrontDomain` | CloudFront frontend domain |
| `CloudFrontDistributionId` | Distribution ID for invalidations |
| `GitHubActionsRoleArn` | Role ARN for GitHub Actions secret `AWS_DEPLOY_ROLE_ARN` |
| `LambdaFunctionName` | Production Lambda function name |
| `LambdaDevFunctionName` | Development Lambda function name |

Retrieve outputs later:

```bash
aws cloudformation describe-stacks \
  --stack-name StickerSnapStack \
  --region ap-southeast-1 \
  --query "Stacks[0].Outputs" \
  --output table
```

## Commands

Install dependencies:

```bash
npm install
```

Bootstrap once per account and region:

```bash
cdk bootstrap aws://$(aws sts get-caller-identity --query Account --output text)/ap-southeast-1
```

Preview changes:

```bash
npm run diff
```

Deploy:

```bash
npm run deploy
```

Synthesize CloudFormation:

```bash
npm run synth
```

Destroy stack-managed resources:

```bash
npm run destroy
```

S3 buckets use `RemovalPolicy.RETAIN`, so destroying the stack does not delete the buckets. Delete retained buckets manually only after confirming their contents are no longer needed.

## Frontend Deployment Notes

Build the frontend with either the dev or production Lambda URL:

```bash
cd ../frontend
echo "VITE_LAMBDA_URL=<LambdaDevFunctionUrl-or-LambdaFunctionUrl>" > .env.production
npm run build
```

Upload the build to the frontend bucket and invalidate CloudFront:

```bash
aws s3 sync dist/ s3://<FrontendBucketName> --delete
aws cloudfront create-invalidation \
  --distribution-id <CloudFrontDistributionId> \
  --paths "/*"
```

## CORS

There are two CORS configurations:

- Lambda Function URL CORS, configured in this stack.
- S3 bucket CORS, configured on the assets buckets.

The current CDK values are permissive for development. Before production launch, restrict:

- Lambda Function URL `allowedOrigins` to the frontend CloudFront domain or custom domain.
- S3 bucket `allowedOrigins` to local development and the deployed frontend origins you actually use.

If the browser is uploading to a presigned S3 URL, CORS failures must be fixed on the S3 bucket or the presigned request shape. Adding S3 CORS headers to Lambda responses will not affect direct S3 `PUT` preflight requests.

## Sensitive Information Checklist

Keep these out of commits and public docs:

- Root `.env`
- `frontend/.env.local`
- AWS access keys, secret access keys, and session tokens
- Real Lambda Function URLs if the repository is public
- `infra/cdk.out/`, because it can include account IDs, ARNs, generated bucket names, and deployment metadata
- `.DS_Store`

Items to review before public release:

- Bucket names include the AWS account ID because they are generated as `stickersnap-*-{account}-{region}`.
- CloudFormation outputs expose generated resource names and URLs.
- The GitHub OIDC trust policy must be narrowed from the placeholder to your exact repository.
- Development CORS uses `*`; production should use explicit origins.

## Cost Notes

The stack is mostly usage-based. At small development volumes, costs are dominated by Lambda execution, ECR image storage for the Docker asset, S3 requests/storage, and any CloudFront traffic beyond the free tier. Provisioned concurrency is not enabled in the current stack.
